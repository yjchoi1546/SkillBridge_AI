# 계약 v4 제안 — 난이도 없는 "자료실형" 과제 (합의 전)

작성: AI-A · 2026-11-13 · 상태: **제안 (세 명 합의 필요)**

과제 하나에 회사 자료를 통째로 주고 **"이런 문제가 있다, 풀어 보라"** 로 바꾸자는 제안이다.
기준 자료는 PwC 해커톤 배포 자료(가상 그룹사 1개, CSV 50개, 문서 22개, 업무 흐름 8개, 문제지·제출 양식)이고,
청년 실습용이라 규모는 그 1/5 정도(표 8~12개, 문서 5~8개)를 목표로 한다.

## 1. 무엇이 바뀌나

| | 지금 (v3) | 제안 (v4) |
| --- | --- | --- |
| 과제 수 | 난이도별 3개 (초급·중급·고급) | **과제 1개**, 난이도 없음 |
| 참여자가 받는 것 | 과제 명세 + CSV 1개 | **자료실**: 세계관, 문제 상황, 규칙, CSV 여러 개, 문서 여러 개, 시작 가이드 |
| 범위 | AI 가 정해 줌 | 참여자가 정함 (작게 잡아도 되고 넓게 잡아도 됨) |
| 제출 | 파일 + 과정 기록 | 파일 + **설계 설명 문항별 답 (각 1,000자 이내)** |
| 평가 | 자동 테스트 위주 | 평가 관점 + 필수 시연 3종 + 설계 설명 + (있으면) 자동 테스트 |
| 난이도 대신 | — | 예상 소요 기간, 필요 역량 태그, 시작 가이드 |

난이도를 없애는 이유: 참여자는 기업·직무를 보고 고르고, 열린 문제라 범위로 난이도가 정해진다.
같은 문제를 세 번 설계하지 않으니 생성 시간도 줄어든다 (EXAONE 실측 38분의 대부분이 과제 3개 설계).

## 3. 비공개 (`GenerationResult.evaluation_key`) — 기업·평가 전용

v3 와 같은 자리, 같은 권한. 내용만 넓어진다.

- `hidden_checks`: **데이터에 심은 사실** (예: 주요 고객의 신규 발주는 줄었는데 출하는 계속됨, 이름이 다른 대리점 두 곳이 같은 계좌 사용, POS 중복 전송).
  위치·확인 방법·관련 테스트 포함. 생성기가 실제로 심은 것만 적는다 (LLM 설명이 아니라 생성 설정에서 계산).
- `answers`: 자동 테스트 정답. 형식은 v3 그대로.

## 4. 설계 설명 문항 (`design_questions`)

PwC 제출 화면처럼 문항마다 1,000자 이내로 "왜 그렇게 설계했는지, 무엇을 근거로 했는지" 를 적게 한다.

```text
DesignQuestion: id, title, prompts: list[str] (하위 질문), required: bool, max_chars: int = 1000
```

**기본 문항 7개는 고정**하고, AI 는 하위 질문을 과제 상황에 맞게 구체화만 한다
(예: "회의록의 '원인 미상' 의견을 어떻게 다뤘나요?"). 문항 구성이 과제마다 달라지면 비교·평가가 어렵기 때문이다.

| id | 문항 | 하위 질문 (기본) | 필수 |
| --- | --- | --- | --- |
| `q1_decision` | 고른 업무와 돕는 결정 | 누가, 어떤 상황에서, 무엇을 결정하나요 / 그 결정이 왜 어려운가요 (판단 지연·정보 공백·반복 작업·부서 간 충돌) | 예 |
| `q2_flow` | 시작과 끝 | 어떤 입력으로 시작하나요 / 어떤 확인·판단·승인을 거치나요 / 어떤 계획·작업·상태까지 처리하나요 | 예 |
| `q3_extension` | 내가 더한 것 | 무엇을 더하거나 깊게 다뤘나요 / 내 경험·관심을 어떻게 살렸나요 / 시스템 어디에 쓰였나요 (조회·계산·판단·상태 변경) | 예 |
| `q4_departments` | 다른 부서 영향 | 어느 부서의 어떤 목표·제약에 영향을 주나요 / 그래서 대안·승인·계획·후속 처리가 어떻게 달라지나요 | 예 |
| `q5_data` | 데이터 | 판단에 쓴 자료는 무엇인가요 / 직접 세운 가정·새로 만든 데이터와 그 이유 / 없던 정보는 어떻게 처리했나요 (확인 요청·보류·가정) / 부서 의견은 사실과 구분했나요 | 예 |
| `q6_scope` | 작동 범위 | 실제 작동·모의 처리·설계만으로 나눠 적어요 / AI 가 맡는 일과 사람이 승인하는 지점 | 예 |
| `q7_more` | 추가로 해 본 것 | 대표 시연 밖에서 더 구현·탐구한 것과 지금 상태 | 아니오 |

제출 (`Submission`) 에는 `design_answers: list[DesignAnswer(question_id, answer)]` 를 추가한다.
App 은 문항별 입력칸과 글자 수(0/1,000)를 보여 주고, 필수 문항이 비면 제출을 막는다.
기존 `process_log`(과정 기록)는 남겨 두고 쓸지 말지는 App 이 정한다.

전환 순서 (루트 CLAUDE.md "접점" 절차):
1. AI 가 v4 필드와 새 함수 형태를 **추가**한다. 이 기간에는 `tasks`(3개)·`dataset` 도 계속 채워 지금 App 이 깨지지 않게 한다
   (`tasks` 는 v4 과제에서 코드로 만든 호환용. LLM 을 추가로 부르지 않는다).
2. App 이 v4 화면·DB 로 옮긴다.
3. App 이 알려 주면 AI 가 `tasks`·`dataset`·난이도(`Difficulty`) 를 지운다.

## 6. App 화면에 생기는 일

- **기업**: 초안 화면이 난이도 탭 → **자료실 미리보기** (세계관, 문제 상황, 규칙 표(종류·출처 배지), 파일 목록, 문서 보기, 필수 시연, 설계 문항). 숨은 사실은 기업에게만.
- **개인**: 지원할 때 난이도 선택 제거. 과제 상세 = 자료실 탐색 + 파일 내려받기 + 시작 가이드.
  제출 화면에 **설계 설명 문항 7개** (문항별 1,000자, 필수 표시).
- **백엔드**: 난이도로 과제를 찾는 곳 (`WorkspaceService` 의 `difficulty` 사용처, `Application.difficulty`) 정리. 평가 호출에 과제 전체와 `evaluation_key` 를 넘김.

## 7. 생성 흐름 (AI-A)

```text
기업 입력 (한 줄 + 질문 5개 + 첨부)
 → 요청 분석            빠진 항목은 되묻기 (기존)
 → 세계관·문제 설계      회사·부서·기준일, 문제 상황, 미션
 → 규칙 설계            결정 권한 / 계산식 / 업무 규칙. 기업이 준 것은 company, 없으면 assumed
 → 심을 사실 설계        "데이터로 드러나야 할 이야기" 목록 → 비공개 hidden_checks
 → 자료 설계·생성        표 구조와 ID 관계는 LLM, 행은 코드가 seed 로 생성하며 심을 사실을 정확히 넣는다
 → 문서 생성            규정(사실) / 회의록(주장) / 기사(미확정)
 → 문제지 마무리         필수 시연 3종, 시작 가이드, 설계 문항 하위 질문, 평가 관점, 완성·미완성 예시
 → 검증                 필수 항목, 파일 간 ID 연결, 민감 단어 유출
```

가장 큰 작업은 **자료 생성기** (표 사이 관계 + 심을 사실). 지금 생성기는 열마다 독립된 무작위 값이라 새로 만든다.
