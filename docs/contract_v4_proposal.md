# 계약 v4 제안 — 난이도 없는 "자료실형" 과제 (합의 전)

작성: AI-A · 2026-11-13 · 상태: **제안 (세 명 합의 필요)**

AI 가 한 번 생성할 때 **과제 1개를 높은 품질로** 만든다. 과제 하나에 가상 회사의 자료를 통째로 주고
"이 회사에 이런 문제가 있다, 풀어 보라" 고 제시한다. 기업은 지금처럼 과제를 여러 개 올릴 수 있다 (요청 1건 = 과제 1개).

> 참고한 자료: 삼일PwC 「AX 인재전쟁」 참가자 배포 자료 (v1.5, 2026-10-29).
> 가상 기업 자료실을 주고 업무 하나를 운영 시스템으로 풀게 하는 형식을 참고했다. 문구·데이터는 옮기지 않았고,
> 아래 구조와 문항은 우리 서비스(청년 실습 과제)에 맞게 새로 정리한 것이다.

## 1. 무엇이 바뀌나

| | 지금 (v3) | 제안 (v4) |
| --- | --- | --- |
| 생성 1회 결과 | 같은 주제의 난이도별 과제 3개 | **과제 1개**, 난이도 없음 |
| 참여자가 받는 것 | 과제 명세 + CSV 1개 | **자료실**: 회사 소개, 문제 상황, 규칙, CSV 여러 개, 문서 여러 개, 시작 가이드 |
| 범위 | AI 가 정해 줌 | 참여자가 정함 (작게 잡아도 되고 넓게 잡아도 됨) |
| 제출 | 파일 + 과정 기록 | 파일 + **설계 설명 (문항 3~5개, 각 500자 이내)** |
| 평가 | 자동 테스트 위주 | 평가 관점 + 필수 시연 + 설계 설명 + (있으면) 자동 테스트 |
| 난이도 대신 | — | 예상 소요 기간, 필요 역량 태그, 시작 가이드 |

- 난이도를 없애는 이유: 참여자는 기업·직무를 보고 과제를 고르고, 열린 문제라 스스로 정한 범위가 곧 난이도다.
- 같은 문제를 세 번 설계하지 않는 대신, 그 시간을 **자료의 깊이**(표 사이 연결, 문서, 심어 둔 사실)에 쓴다.
- 규모 목표: 표 8~12개, 문서 5~8개. 청년이 1~2주 안에 다 훑어볼 수 있는 양.

## 2. 공개 과제 (`ProjectDraft`) — 참여자에게 보이는 것

| 필드 | 내용 | v3 에서 |
| --- | --- | --- |
| `title`, `summary`, `domain_tags` | 그대로 | 유지 |
| `skills` | 필요 역량 태그 (탐색 필터) | `tasks[].skills` 를 합쳐 이동 |
| `estimated_effort` | 예상 소요 기간. 예: "1주, 하루 2~3시간" | 신규 |
| `context` | 가상 회사·부서·사람, 기준일, 지금 회사가 고민하는 것 | 유지 |
| `problem` | `situation`(지금 벌어지는 일), `tensions`(부서끼리 이해가 엇갈리는 곳), `mission`(무엇을 만들어 보여줄지), `scope_guide`(범위를 좁히는 요령) | 신규 |
| `rules` | 규칙 + 출처(`company`/`assumed`) + **종류 `category`**: `authority`(누가 승인하나) / `calculation`(어떻게 계산하나) / `business`(업무 기준) | `category` 추가 |
| `datasets` | CSV 여러 개. 다른 표를 가리키는 열에는 `references` 표시 (예: `stores.store_code`) | `DatasetColumn.references` 추가 |
| `documents` | 문서 여러 개 (`filename`, `title`, `content` 마크다운). **성격 `kind`**: `policy`(규정·계약) / `record`(기록) / `opinion`(회의록·메모 등 부서 의견) / `external`(기사 등 확인 안 된 외부 정보) | 신규 |
| `data_notes` | 미리 알려 주는 데이터 한계 | 유지 |
| `required_demos` | 시연할 상황 3개: `normal`(평소) / `changed`(조건이 바뀜) / `exception`(정보가 없거나 승인이 안 남) | `tasks[].scenarios` 를 과제 단위로 이동 |
| `start_guide` | `open_points`(자료만으로는 답이 안 나오는 곳), `questions`(시작할 때 던져 볼 질문), `first_files`(먼저 볼 파일) | 신규 |
| `deliverables` | 제출물 | 과제 단위로 이동 |
| `design_questions` | **설계 설명 문항** (아래 4절) | 신규 |
| `review_criteria` | 평가 관점 (`RubricItem` 재사용) | `tasks[].rubric` 을 과제 단위로 |
| `done_examples`, `not_done_examples` | 완성·미완성 예시 | 과제 단위로 이동 |
| `tests` | 자동 확인 항목 (선택). 정답은 비공개 쪽 | 과제 단위로 이동 |
| ~~`tasks`~~, ~~`dataset`~~ | App 이 옮겨 간 뒤 제거 | 제거 예정 |

## 3. 비공개 (`GenerationResult.evaluation_key`) — 기업·평가 전용

v3 와 같은 자리, 같은 권한. 내용만 넓어진다.

- `hidden_checks`: **데이터에 심어 둔 사실** (예: 주요 고객의 신규 주문은 줄었는데 출하는 이어짐, 이름이 다른 거래처 두 곳의 계좌가 같음, 같은 매출이 두 번 들어옴).
  위치·확인 방법·관련 테스트를 적는다. 생성기가 실제로 심은 것만 적는다 (LLM 설명이 아니라 생성 설정에서 계산).
- `answers`: 자동 테스트 정답. 형식은 v3 그대로.

## 4. 설계 설명 문항 (`design_questions`)

결과물만으로는 "왜 그렇게 만들었는지" 가 안 보이므로, 제출할 때 짧은 설명을 받는다.

```text
DesignQuestion: id, title, prompts: list[str] (하위 질문), required: bool, max_chars: int = 500
```

- **기본 문항 3개** + 과제에 꼭 필요하면 AI 가 **최대 2개까지 추가** (총 5개 이하).
- 기본 문항도 AI 가 과제 상황에 맞게 하위 질문 문구를 바꿀 수 있다. 예: "재고 담당자의 발주 결정" 처럼 그 과제의 사람·결정을 넣는다.
- 문항마다 500자 이내.

| id | 문항 (기본) | 하위 질문 예 | 필수 |
| --- | --- | --- | --- |
| `q_target` | 무엇을 풀었나 | 누구의 어떤 일을 돕기로 했나요? 많은 문제 중 그걸 고른 이유는? | 예 |
| `q_flow` | 어떻게 동작하나 | 무엇을 받아서, 어떤 순서로 처리하고, 무엇을 남기나요? 사람이 확인·승인하는 곳은 어디인가요? | 예 |
| `q_basis` | 무엇을 근거로 했나 | 어떤 파일·문서를 썼나요? 자료에 없던 것은 어떻게 했나요 (물어보기·미루기·가정)? 부서 의견과 사실을 어떻게 나눴나요? | 예 |

AI 가 추가할 수 있는 문항 예: 다른 부서에 미치는 영향 (부서 간 갈등이 핵심인 과제), 조건이 바뀌었을 때의 대응, 다음에 더 하고 싶은 것 (선택 문항).

제출 (`Submission`) 에는 `design_answers: list[DesignAnswer(question_id, answer)]` 를 추가한다.
App 은 문항별 입력칸과 글자 수(0/500)를 보여 주고, 필수 문항이 비면 제출을 막는다.
기존 `process_log`(과정 기록)는 남겨 두고 쓸지 말지는 App 이 정한다.

## 5. 함수 (`ai/src/api/`)

| 함수 | v4 | 비고 |
| --- | --- | --- |
| `ask_clarifying_questions`, `generate_project`, `revise_project` | 이름·인자 그대로. 결과 `draft` 가 v4 형태 | — |
| `generate_followup_questions` | `task` 대신 **`project: ProjectDraft`** 를 받는 형태 추가 | AI-B |
| `evaluate_submission` | `task`·`dataset` 대신 **`project`** 를 받는 형태 추가. 설계 설명·필수 시연·평가 관점으로 평가 | AI-B. 리포트 형식은 B 제안 |

전환 순서 (루트 CLAUDE.md "접점" 절차):
1. AI 가 v4 필드와 새 함수 형태를 **추가**한다. 이 기간에는 `tasks`(3개)·`dataset` 도 계속 채워 지금 App 이 깨지지 않게 한다
   (`tasks` 는 v4 과제에서 코드로 만든 호환용. LLM 을 추가로 부르지 않는다).
2. App 이 v4 화면·DB 로 옮긴다.
3. App 이 알려 주면 AI 가 `tasks`·`dataset`·난이도(`Difficulty`) 를 지운다.

## 6. App 화면에 생기는 일

- **기업**: 초안 화면이 난이도 탭 → **자료실 미리보기** (회사 소개, 문제 상황, 규칙 표(종류·출처 배지), 파일 목록, 문서 보기, 시연 상황, 설계 문항). 심어 둔 사실은 기업에게만.
- **개인**: 지원할 때 난이도 선택 제거. 과제 상세 = 자료실 탐색 + 파일 내려받기 + 시작 가이드.
  제출 화면에 **설계 설명 문항 3~5개** (문항별 500자, 필수 표시).
- **백엔드**: 난이도로 과제를 찾는 곳 (`WorkspaceService` 의 `difficulty` 사용처, `Application.difficulty`) 정리. 평가 호출에 과제 전체와 `evaluation_key` 를 넘김.

## 7. 생성 흐름 (AI-A)

```text
기업 입력 (한 줄 + 질문 5개 + 첨부)
 → 요청 분석            빠진 항목은 되묻기 (기존)
 → 회사·문제 설계        회사·부서·기준일, 문제 상황, 미션
 → 규칙 설계            승인 / 계산 / 업무 기준. 기업이 준 것은 company, 없으면 assumed
 → 심을 사실 설계        "데이터로 드러나야 할 이야기" 목록 → 비공개 hidden_checks
 → 자료 설계·생성        표 구조와 ID 관계는 LLM, 행은 코드가 seed 로 생성하며 심을 사실을 정확히 넣는다
 → 문서 생성            규정 / 기록 / 부서 의견 / 외부 기사
 → 마무리               시연 상황, 시작 가이드, 설계 문항, 평가 관점, 완성·미완성 예시
 → 검증                 필수 항목, 파일 간 ID 연결, 민감 단어 유출
```

가장 큰 작업은 **자료 생성기** (표 사이 관계 + 심을 사실). 지금 생성기는 열마다 독립된 무작위 값이라 새로 만든다.
