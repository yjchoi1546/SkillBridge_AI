# 예시 과제: 지점별 주간 매출 보고와 후속 조치

> **이 문서의 용도**
> SkillBridge AI 가 만들어야 하는 **과제 품질의 기준 예시**다. 세 명이 "이 수준을 목표로 한다"를 맞추는 데 쓰고,
> 나중에 과제 생성 프롬프트의 모범 예시(few-shot)로도 쓴다.
> 등장하는 회사·지점·인물·수치는 모두 **가상**이다. 외부 대회 문제지를 옮기지 않고 구조만 참고해 새로 썼다.
> 참고한 자료: 삼일PwC 「AX 인재전쟁」 참가자 자료 (https://axacademy.ai/axwar/samilpwc-1).

읽는 순서: **① 기업이 입력한 것** → **② AI 가 만든 공개 과제** → **③ 지금 스키마와의 차이**.

## ① 기업 입력 (기업 회원이 요청 화면에 쓰는 것)

한 문장 요청(`ai/tests/fixtures/requests.jsonl` 첫 줄)에 질문 5개의 답이 붙은 형태다.
질문 2~5가 비어 있으면 AI 가 `ask_clarifying_questions` 로 되묻는다.

| 질문 | 기업 답변 (예시) |
| --- | --- |
| 0. 한 줄 요청 | 매주 엑셀로 취합하는 지점별 매출 보고서 작성 시간을 줄이고 싶습니다. |
| 1. 어떤 업무가 막히나요? | 매주 월요일 오전 영업관리팀 2명이 지점별 엑셀을 합쳐 보고서를 만듭니다. 반나절이 걸리고, 지점마다 양식이 조금씩 달라 숫자가 자주 틀립니다. |
| 2. 그 결과로 누가 어떤 결정을 하나요? | 지역본부장이 매출이 떨어진 지점을 보고 재고 재배치나 프로모션을 결정합니다. 결정은 화요일까지 나와야 수요일 물류 배차에 반영됩니다. |
| 3. 판단 규칙이 있나요? | 전주 대비 순매출이 20% 이상 떨어진 지점은 본부장에게 보고합니다. 매출은 부가세 제외, 반품 차감 금액으로 봅니다. |
| 4. 어떤 데이터를 쓰나요? | 지점 POS 일별 매출 엑셀, 지점 목록. 지점명이 사람마다 다르게 적히고, POS 오류로 같은 날 매출이 두 번 올라오기도 합니다. |
| 5. 잘 됐다는 건 어떤 상태인가요? | 월요일 10시 전에 보고서가 나오고, 수작업 결과와 숫자가 일치하고, 보고 대상 지점이 빠지지 않는 것. |

추가 설정: 희망 직무 `데이터 분석`, `업무 자동화` / 데이터 범위 `synthetic_public` /
민감 단어 `실제 회사명`, `실제 지점명`, `내부 POS 시스템명` / 일반화 `medium`(업종까지 일반화)

> AI 가 **지어내도 되는 것**: 회사 세계관, 지점 이름, 데이터 값, 데이터 함정.
> AI 가 **지어내면 안 되는 것**: 판단 규칙(20%), 결정권자, 마감 시각. 입력에 없으면 되묻거나 **(가정)** 으로 표시한다.

## ② AI 가 만든 공개 과제 (개인 회원에게 보이는 것)

### 2-1. 가상 회사 세계관

**온새리빙 (가상 기업)** — 생활용품 오프라인 매장 체인.

| 항목 | 내용 |
| --- | --- |
| 지점 | 13곳. 수도권본부 7곳, 영남본부 6곳 (그중 1곳은 2026-03-02 신규 개점) |
| 데이터 기간 | 2025-01-06(월) ~ 2026-04-05(일), 65주 |
| **기준일 ("오늘")** | **2026-04-06(월) 09:00** — 직전 주(2026-W14)의 보고서를 만드는 시점 |
| 금액 단위 | 원, 부가세 제외. 순매출 = 총매출 − 반품 |

| 부서 / 사람 | 목표 | 제약 |
| --- | --- | --- |
| 영업관리팀 (보고서 작성) | 월요일 10시 전 정확한 보고서 | 2명, 지점 양식 제각각 |
| 지역본부장 (결정권자) | 하락 지점에 빠르게 조치 | 화요일까지 결정해야 수요일 배차 반영 |
| 물류팀 | 재고 재배치 실행 | 주 1회 배차, 트럭 1대당 최대 3개 지점 |
| 마케팅팀 | 지점 프로모션 집행 | 프로모션 재고는 물류 재배치와 같은 창고 재고를 쓴다 |

**핵심 문제**: 보고서가 늦고 틀리면 본부장 결정이 하루 밀리고, 그 주 배차를 놓쳐 하락 지점이 한 주 더 방치된다.

### 2-3. 데이터 명세

| 파일 | 컬럼 | 설명 |

**숨은 함정** (참여자에게 알리지 않는다 — 기업·평가 전용, seed 로 위치가 고정되어 정답 재현 가능)

| ID | 함정 | 위치 | 잡았는지 확인하는 방법 |
| --- | --- | --- | --- |
| H1 | POS 재전송으로 같은 행 중복 | 2026-03-31, 수도권 3개 지점 | 중복 제거 후 행 수 = 정답 |
| H2 | `store_code` 가 비어 있고 지점명만 변형 표기 (`강남점` / `강남 점` / `강남`) | W14 일부 행 | 지점 수 = 13, 지점별 합계 = 정답 |
| H3 | 하루 데이터 누락 (POS 장애) | 2026-04-02, 영남 1개 지점 | 보고서에 "누락일 있음" 표시, 0으로 채워 하락 판정하지 않음 |
| H4 | 리모델링 휴점 | 2026-03-30~04-05, 영남 1개 지점 (`stores.csv` 의 `note`) | R3 적용 → "휴점" 표시 |
| H5 | 신규 개점 지점 | 2026-03-02 개점 지점 | R4 적용. 개점 후 4주 데이터로 판정했다면 근거를 설명했는지 확인 |

### 2-4. 난이도별 과제

#### 초급 — 주간 매출 집계 자동화

- **목표**: 일별 매출을 정제해 지점·주차별 순매출 표를 자동으로 만든다.
- **범위**: 정제(중복·지점명 통일)와 집계까지. 하락 판정·보고는 범위 밖.
- **단계**: 데이터 불러오기 → 지점명을 `store_code` 로 통일 → 중복 제거 → 순매출 계산 → 주차별 집계 → 결과 파일 저장
- **제출물**: 실행 코드, `weekly_summary.csv`, 정제 과정 메모(무엇을 왜 바꿨는지)
- **기술 태그**: Python, pandas, 데이터 정제

| 시나리오 | 상황 | 기대 동작 |
| --- | --- | --- |
| 정상 | W14 데이터 집계 | 13개 지점 순매출 표 |
| 조건 변경 | 지점명 변형 표기가 섞인 행 발견 (H2) | 지점 목록 기준으로 통일, 통일 규칙을 메모에 기록 |
| 정보 부족 | 같은 행이 두 번 있음 (H1) | 중복으로 판단한 근거와 제거 건수 기록 |

- **완성**: 코드를 다시 돌리면 같은 표가 나오고, 정제로 바뀐 행 수가 메모에 있다.
- **미완성**: 엑셀에서 손으로 고친 결과 표만 있다 / 지점이 13개가 아니다.

#### 중급 — 하락 지점 판정과 보고 목록

- **목표**: 규칙 R1~R4 를 적용해 본부장 보고 대상 지점 목록을 근거와 함께 만든다.
- **범위**: 초급 결과 + 판정 + 보고서. 실제 조치 실행은 범위 밖.
- **단계**: 초급 집계 재사용 → 전주 대비 증감률 계산 → R1 판정 → 예외(R3 휴점, R4 신규, H3 누락) 처리 → 보고서 작성
- **제출물**: 실행 코드, `report_targets.csv`(지점, 증감률, 판정, 근거), 보고서(1쪽)
- **기술 태그**: Python, pandas, 규칙 기반 판정, 보고서 자동화

| 시나리오 | 상황 | 기대 동작 |
| --- | --- | --- |
| 정상 | W14 판정 | 보고 대상 목록 + 지점별 근거 |
| 조건 변경 | `sales_correction.csv` 도착 (W13 매출 정정) | 다시 계산, 판정이 바뀐 지점과 이유를 보고서에 표시 |
| 정보 부족 | 하루 누락 지점 (H3) | 0으로 채워 하락 판정하지 않고 "확인 필요" 로 보류, 영업관리팀 확인 요청 문구 생성 |

- **완성**: 같은 입력이면 같은 목록, 정정본 반영 전후 차이가 보인다, 가정 규칙(R3·R4)을 **(가정)** 으로 구분해 적었다.
- **미완성**: 증감률 표만 있고 판정이 없다 / 휴점 지점을 하락으로 보고했다.

#### 고급 — 보고에서 조치까지 이어지는 운영 흐름

- **목표**: 보고 → 본부장 승인 → 물류·마케팅 작업 생성 → 상태 변경까지 실제로 이어지는 작은 시스템을 만든다.
- **범위**: 중급 결과 + 승인 흐름 + 작업 생성 + 상태 이력. 실제 외부 시스템 연동 대신 **모의 회신**을 쓴다.
- **단계**: 보고 대상 지점마다 조치안(재고 재배치 / 프로모션) 제안 → 본부장 승인 요청(모의) → 승인 시 물류 작업 생성, 지점 상태를 "조치 중" 으로 변경 → 다음 주 판정에 상태 반영
- **제출물**: 실행 가능한 코드(CLI 또는 웹), 상태 이력 로그, 시연 기록(3개 시나리오), 설계 메모
- **기술 태그**: Python, 상태 관리, 워크플로 자동화, (선택) LLM 활용

| 시나리오 | 상황 | 기대 동작 |
| --- | --- | --- |
| 정상 | 하락 지점 2곳 승인 | 물류 작업 2건 생성, 배차 제약(트럭 1대당 3개 지점) 안에서 배정, 상태 변경 |
| 조건 변경 | 본부장이 기준을 20% → 15% 로 낮춤 | 보고 대상이 늘고, 배차 한도를 넘으면 우선순위를 정해 다음 주로 넘김 |
| 거절 | 본부장이 재배치를 거절 | 대안으로 마케팅 프로모션 요청 생성. 단, 같은 창고 재고를 쓰므로 **다른 지점 프로모션 재고가 줄어드는 영향**을 표시 |

- **완성**: 승인·거절 결과에 따라 실제로 상태가 바뀌고, 바뀐 상태가 다음 판단에 쓰인다. 다른 부서 영향이 1개 이상 드러난다.
- **미완성**: 대시보드나 권고문만 있다 / 승인 버튼이 있어도 상태가 바뀌지 않는다.

| 기준 | 설명 | 자동 판정 |
| --- | --- | --- |

| 규칙 적용 | R1~R4 판정 결과가 정답과 일치 | 예 |

| 운영 흐름 (고급) | 승인 결과가 상태와 다음 판단에 반영 | 아니오 (시연 확인) |

| ID | 난이도 | 종류 | 내용 |
| --- | --- | --- | --- |
| T01 | 초급 | auto | 중복 제거 후 W14 행 수 = 정답 (H1) |
| T02 | 초급 | auto | 고유 지점 수 = 13 (H2) |
| T03 | 초급 | auto | W14 지점별 순매출이 정답과 ±1원 이내 |
| T04 | 중급 | auto | 보고 대상 지점 집합 = 정답 |
| T05 | 중급 | auto | 휴점 지점(H4) 판정 = "휴점" |
| T06 | 중급 | auto | 정정본 반영 후 보고 대상 집합 = 정답 |
| T07 | 중급 | manual | 누락일(H3) 지점을 "확인 필요" 로 보류했는가 |
| T08 | 고급 | manual | 3개 시나리오 시연에서 상태가 실제로 바뀌는가 |
| T09 | 고급 | manual | 거절 시 다른 부서 영향이 드러나는가 |

auto 테스트의 정답은 데이터를 만든 seed 로 미리 계산해 둔다 (참여자 코드 출력과 비교).

## ③ 스키마와의 차이 — 계약 v3 로 반영됨

아래 표는 v2 기준으로 정리한 차이이고, **계약 v3 로 반영했다.** 실제 필드 이름과 App 할 일은 [ai/CONTRACT.md](../ai/CONTRACT.md) "v2 → v3 변경점".
제안과 달라진 점: 질문 5개는 `ProjectRequest.intake`, 숨은 함정과 테스트 정답은 `ProjectDraft`·`TestCase` 가 아니라
`GenerationResult.evaluation_key` 에 둔다 (App 이 `draft.tasks` 를 그대로 공개하므로 그 안에 두면 정답이 샌다).

| 필요한 것 | 지금 | 제안 | 영향 |
| --- | --- | --- | --- |
| 기업 입력 질문 5개 | `request_text` 한 칸 | 질문별 필드 추가 (기존 필드 유지) | App 요청 화면 |
