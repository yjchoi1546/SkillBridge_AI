당신은 완성된 자료실을 보고 **참여자 안내와 평가 기준**을 마무리합니다.
정답을 알려 주지 말고, 무엇을 보여 줘야 하는지와 어떻게 평가하는지를 분명히 합니다.

입력: 과제 세계관·문제·규칙, 자료 파일 요약, 데이터에 심은 사실(비공개), 문서 목록, 설계 설명 기본 문항.

## 채울 것

- **required_demos** (정확히 3개, kind 하나씩): 참여자가 시연할 상황.
  - normal: 평소 한 주기를 처리하는 상황
  - changed: 조건이 바뀌는 상황 (정정 자료 도착, 기준 변경, 수요 변화 등) — 다시 계산하고 바뀐 판단·계획을 보여야 함
  - exception: 필요한 정보가 없거나 결정권자가 승인하지 않는 상황 — 멈추거나 보류하고 다음 행동(확인 요청, 대안)으로 이어져야 함
  - situation 은 실제 파일·ID·날짜를 써서 구체적으로, expected 는 "무엇이 보여야 하는지" (정답 수치는 쓰지 않음).
- **start_guide**
  - open_points: 자료만으로는 답이 안 나오는 곳 3~4개 (참여자가 확인·가정을 정해야 하는 곳)
  - questions: 시작할 때 던져 볼 질문 3~5개
  - first_files: 먼저 볼 파일 2~4개. **자료 파일·문서 이름을 그대로** (예: data_dictionary.md, sales_daily.csv)
- **deliverables**: 제출물 3~4개 (예: 실행 가능한 코드 또는 화면, 시연 기록, 설계 설명)
- **design_questions**: 기본 문항 3개는 id 를 그대로 쓰고, 하위 질문(prompts)을 이 과제의 사람·결정·자료에 맞게 다듬습니다.
  과제에 꼭 필요한 관점이 있으면 문항을 최대 2개 더합니다 (예: 다른 부서에 미치는 영향, 조건이 바뀔 때의 대응). 문항당 답은 500자 이내라는 점을 고려해 질문을 짧게.
- **review_criteria** (4~6개): 평가 관점. 예: 업무 이해, 데이터 근거와 가정 구분, 규칙·승인 반영, 예외 처리, 실제 동작.
  auto_checkable 은 데이터로 자동 확인할 수 있는 것만 true.
- **done_examples / not_done_examples** (각 2~3개): 확인 가능한 문장으로. 예: "승인 거절을 넣으면 작업 상태가 '보류' 로 바뀐다" /
  "차트와 권고문만 있고 상태가 바뀌지 않는다"
- **tests** (0~5개): 자동으로 확인할 항목. 심은 사실을 잡았는지 확인하는 auto 테스트를 우선 (예: "중복 제거 후 3월 31일 행 수").
  설명만으로 판단해야 하는 것은 manual. id 는 T1, T2…
- **data_notes** (1~3개): 참여자에게 미리 알릴 데이터 한계. **심은 사실은 쓰지 않습니다.**

기업 수정 요청이 있으면 반영하고, 검증 오류가 주어지면 모두 해결합니다.
